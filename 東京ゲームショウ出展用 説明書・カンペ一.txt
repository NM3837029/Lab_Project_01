1. 作品の基本情報
============================================================

1-1. 名前

  タイトル画面に出る作品名   Editron（エディトロン）
  副題                       2Dアクションゲームのためのゲームエンジン
  ウィンドウタイトル         Lab Project 01 - 編集して進む2Dアクション
  リポジトリ／実行ファイル名 Lab_Project_01

Lab_Project_01 は開発上の名前です。来場者に見えるのは Editron のほうです。
名前は assets/game_config.json の title_screen に入っており、
Lab_Editor の「ゲーム設定」から変更できます。


1-2. 位置づけ

エンジンとエディタを作り、そのエンジンとエディタで作ったゲームを
7ステージ同梱している、という構成です。
「作る道具」と「その道具で作ったもの」を同時に展示している状態にあたります。

同梱ステージはすべて Lab_Editor で作ったもので、
タイルの配置、敵の当たり判定、敵の動きそのものまで、
すべてエディタ側から編集できます。

1-4. この作品の中心にある考え方

中心は「編集」です。巻き戻しはその道具のひとつにすぎません。

プレイヤーはプレイ中に、敵やしかけに対して
一時停止・巻き戻し・早送り・拡大縮小・回転・向き反転・移動・
画面エフェクト・区間カット、という操作を掛けられます。

その結果として、敵は「倒す相手」ではなく「働かせる道具」になります。
たとえば砲台は、普通に見れば障害物ですが、
向きを反転させると弾がプレイヤー側の弾に変わり、
他の敵や壊せる壁に当たるようになります。

同じ操作でも、相手によって起きることが変わります。
トゲは45度以上倒すと無害な足場になり、砲台は傾けると狙いが固定されます。
この対応関係は2-4にまとめてあります。

2. 遊びの仕組み
============================================================

2-1. 操作

動かす

  A / D                  左右に歩く
  W                      ジャンプ
  Enter                  ショット（画面内を左クリックでも可）
  Shift                  ダッシュ（ダッシュ能力を取ったあと）

編集する

  R 長押し               時間を巻き戻す
  Space                  一時停止 / 再開
  Space 中に →           コマ送り
  F                      早送り（2倍）
  T                      画面の色を変える（なし→赤→緑→青→なし）
  Z / X / C              ズーム / 暗くする / 明るくする
  右クリック             敵やしかけを選んでメニューを出す
  ドラッグ               動かす
  S + ドラッグ           大きさを変える
  W + ドラッグ           高さを変える（しかけのみ）
  R + ドラッグ           回転させる
  Ctrl + タイムライン帯を2回クリック   カット（区間を丸ごと飛ばす）

そのほか

  Esc                    どの画面でもゲームを終了する
  BackSpace または X     ステージ選択からタイトルへ戻る
  矢印キー全押し         ゲームを閉じて Lab_Editor へ戻る（開発用の隠し操作）
  M                      効果音のミュート切り替え
  F3                     デバッグ表示の切り替え

移動が A/D、ジャンプが W である点は、よく取り違えられます。
Space は一時停止です。以前はジャンプでしたが、
プレイテストの指摘を受けて一時停止へ変えた経緯があります
（DrawPixel.cpp:4823 のコメントに記録が残っています）。

HUD は画面左上の枠にあります。上段がコインの取得枚数、
下段が編集コストゲージです。ゲージは残り2割を切ると赤く点滅します。


2-2. 編集ツールは6カテゴリ

内部的には6つのフラグで管理されています
（struct EditToolFlags、DrawPixel.cpp:404）。

  rewind         時間巻き戻し
  pause          一時停止
  fastForward    早送り
  screenEffect   Z/X/C（ズーム・明暗）と T（色フィルタ）をまとめたもの
  objectEdit     右クリックによる個別オブジェクト編集（選択とメニュー全体）
  cut            下部タイムラインでの区間カット

この6つは、ステージ単位で個別にON/OFFできます。
ステージJSONの allowed_edit_tools で設定し、Lab_Editor から編集できます。

さらに、アイテムで恒久的に解禁する仕組みもあります
（DrawPixel.cpp:449 の unlockedEditTools）。
これはステージをまたいで保持され、リトライでもクリアされません。
アイテム側は grant_ability に "UnlockEditTool:Rewind" のような
文字列を入れて指定します。

判定は「ステージで許可されている、または、アイテムで解禁済み」の
どちらかが真なら使える、という形です（DrawPixel.cpp:3528）。


2-3. 編集コストゲージの数値

編集はゲージを消費します（struct EditCostSettings、DrawPixel.cpp:420）。
この数値はステージ単位で上書きできます。

継続して押している間、毎秒引かれるもの

  巻き戻し                18.0 / 秒
  早送り                  10.0 / 秒
  画面エフェクト（Z/X/C、色フィルタが非ゼロの間） 8.0 / 秒
  一時停止                 4.0 / 秒

1回ごとに一括で引かれるもの

  カットを1本作る          20.0 ＋ 1.2 × 飛ばすタイル数
  個別の巻き戻し／一時停止のトグル   8.0
  速度変更（±0.5）         6.0
  全リセット              10.0
  色フィルタを1段階進める   5.0
  向き反転                 4.0

回復

  何も使っていない間        6.0 / 秒
  ゲージの最大値          100.0

仕様として押さえておく点

 ・ドレインは加算式です。巻き戻しと一時停止と早送りと画面効果を
   同時に使うと毎秒40まで膨らみます。
 ・ひとつでも継続系が動いている間は回復しません（DrawPixel.cpp:8825）。
 ・ゼロになると継続系が強制解除され、専用の効果音が鳴ります。
 ・ドラッグでの変形（移動・拡大縮小・回転）は無料です。
   コストが掛かるのは右クリックメニュー経由の操作だけです。
 ・一時停止の「解除」は常に無料です。止めるときだけ掛かります。
 ・色フィルタを「なし」に戻す遷移も無料です。


2-4. 編集リアクション：誰に何をすると何が起きるか

全編集操作について、全23種の敵と全26種のギミックが固有の反応を返します。
仕組みの実装は4-6に、以下は遊びとして現れる内容です。

全オブジェクトに共通して効くもの

 ・一時停止した敵は足場になり、接触ダメージも与えなくなる
 ・巻き戻し中の敵は過去の残像あつかいで、すり抜けられる
 ・拡大すると重く鈍くなり、縮小すると軽く速くなる
 ・画面が暗いと敵の索敵範囲が0.6倍に狭まり、明るいと1.4倍に広がる
 ・早送り中は全タイプで攻撃間隔が詰まる

回転（R + ドラッグ）についての基準の向き

敵はタイプごとに「編集されていないときにどちらを向いているか」を持っており、
回転はその基準を回す形で効きます。回転方向はスプライトの見た目と一致します。

  基準が下   ドッスン（落ちてくる敵）
             落下方向そのものが変わる。90度倒せば真横へ、180度で真上へ飛ぶ
  基準が上   飛びかかり、ジャンプ、各種射撃、テレポート
             跳躍角・射出方向・出現方角が変わる
  基準が前   突進、歩行、追跡、浮遊
             突進は傾けた角度どおりに一直線へ飛ぶ。
             歩行系は水平成分だけを使うので、90度倒すと止まり、
             180度で逆走する（宙に歩き出すことはない）

落下中と突進中は重力を打ち消して軸方向へ加速します。
重力を残すと斜めに向けても途中で失速して真下に落ちてしまうためです。
真下を向いている間は従来の自由落下と完全に同じ速さになります。

向き反転についての固有の反応

  固定砲台・照準砲台   弾がプレイヤー側の弾になり、他の敵に当たるようになる。
                       ブロックを壊す力も持つ
  巡回砲台             プレイヤーを見つけても撃たず、反対側へ逃げ出す
  巡回敵               巡回範囲の端を待たず、その場で折り返す
  突進・追跡・歩行・浮遊  プレイヤーを追うのをやめ、逃げる向きへ進む
  落下リフト、重量スイッチ、色/明暗ゾーン   効果が裏返る（沈む→浮上 など）

縦向きが基準の敵（ドッスンや射撃系）では、反転は基準の向きを
向いている側へ30度振ります。ドッスンを反転させると斜めに落ちるのはこのためです。

砲台についての仕様

 ・傾けると砲身がその向きへ固定され、次の一発だけそこへ撃つ。
   撃つと傾きを消費してプレイヤー追尾に戻る
 ・回るのは砲身だけで、台座は置いたときの姿勢のまま。
   敵の定義に bodyIgnoresTilt というフラグがあり、
   これがONの敵だけ本体の絵を配置時の姿勢で描く。既定はOFF
 ・弾は砲身が指している向きへそのまま飛ぶ

当たり判定は常に軸平行の矩形（AABB）です。
横倒しにしたドッスンの判定が横長になることはありません。


2-5. アセット単位の編集禁止

「この敵だけは拡大させたくない」といった縛りを、アセット定義ごとに設定できます。
拡大縮小・回転・移動・向き反転・一時停止・巻き戻し・速度変更の7項目です。

ステージ単位の「使える編集ツール」とは別の軸です。
ステージ側は「そのステージでどの道具を使えるか」、
こちらは「このオブジェクトに対して何をしてよいか」を決めます。

複数まとめて選んだ場合は、禁止されている相手だけが除外されます。


2-6. 壊せる地形の3種類

壊せる地形は画像を持たず色だけのブロックにしてあるので、
普通の地形と見分けがつくようになっています。

  桃色   弾でしか壊れない。プレイヤーは弾を撃てないので、
         砲台を反転させて味方撃ちにする必要がある
  土色   叩きつけ（ドッスンの着地衝撃）でしか壊れず、
         しかも等倍では壊れない。1.3倍以上に拡大したドッスンが要る
  青緑   体当たりでしか壊れない。突進してくる敵の向きを変えてぶつける

破壊条件はタイルごとに設定できます。項目は
叩きつけ／体当たり／弾／手動クリック の4つのON/OFFと、
必要倍率（0なら大きさを問わない）、破壊音のIDです。
既定は全てオフなので、触らない限り地形は壊れません。

壊れたマスは「壊れてから何フレーム経ったか」を覚えていて、
巻き戻している間はその時間も巻き戻り、0まで戻ると元のタイルへ戻ります。
ただし巻き戻せる時間（約10秒）より前に壊したマスは戻りません。
プレイヤーが重なっているマスは、退くまで復活を待ちます
（復活と同時に地形へ埋まって抜け出せなくなるのを防ぐため）。

ギミックとして置く「壊せるブロック」も別にあります。違いは次のとおりです。

  地形タイル             マップに敷く。大量に置いても軽い。
                         傾かないので自重で崩すことはできない。大きさも変えられない
  壊せるブロック（ギミック） 1個ずつ置く。傾けて自重で崩せる。大きさも変えられる。
                         個数ぶん重くなる


2-7. ステージごとの設計

同梱は7本です。前半4本は編集ツールが全部使え、
後半3本は使える道具を2つずつに絞ってあります。
そのステージで何が使えるかは、画面左の EDIT TOOLS 欄に表示されます。

  ステージ              マス     使える編集ツール
  はじまりの草原        80×15    すべて
  編集のとびら         120×15    すべて
  たての塔（縦）        20×64    すべて
  いろの回廊           100×15    すべて
  かたむく丘            96×15    一時停止、オブジェクト編集
  ほりぬきの坑道       110×20    巻き戻し、オブジェクト編集
  わきあがる縦坑（縦）  24×72    一時停止、オブジェクト編集

道具を減らしてあるのは難易度を上げるためではなく、
解き方を一本道にするためです。使える道具が少ないほど
「何をすればいいか」ではなく「どう使うか」を考える形になります。

後半3本の仕掛けと、その成立条件

かたむく丘（地上）

 ・入口の上段はコインの並んだ板の道だが途中で切れており、その先は棘の穴。
   本当の道は下段
 ・全高の壁の足元に桃色のブロックが埋まっている。
   砲台の弾はもともとここへ当たるが、敵の弾のままでは壊れない。
   砲台を反転させて味方撃ちにすると通る。
   壁との間に立てば、追尾している弾がそのまま壁へ届く
 ・横穴を塞ぐ土色の壁は、ドッスンを横へ回して飛ばし、
   さらに拡大しないと砕けない。壁は左右どちらにもあり、左の壁の中にコインがある
 ・谷は素では絶対に届かない距離。追ってきたドローンを空中で止めて踏み台にする
 ・低い天井の通路にいる敵食らいは、巡回している敵を誘導して相討ちさせる
 ・最後の青緑の壁は、突進してくる敵を反転させてぶつけさせる

ほりぬきの坑道（地下）

 ・岩盤をくり抜いた2階建て
 ・上層の行き止まりで床が土色。ドッスンを拡大して砕き、下層へ落ちる
 ・下層の広間では機械いもむしが斜めに跳ね回っている。
   回して逸らすか、跳ね返りの周期を読んで抜ける
 ・上層へ戻る唯一の道は天井に埋まった桃色のブロック。
   砲台を真上へ回し、反転させて撃ち抜く
 ・重量スイッチは、箱を拡大して踏ませる
 ・近道に見えるちくわ床は罠。乗ると抜け落ち、跳んでは出られない縦穴に落ちる。
   巻き戻すか、底の箱を拡大して踏み台にすれば出られる

わきあがる縦坑（下から上）

 ・巻き戻しが使えない。落ちたら下まで戻る
 ・登りは3マスずつの棚で組んであるので、基本は素で登れる
 ・1箇所だけ6マスの断絶があり、そこは追ってきたドローンを止めて中継にする
 ・途中の部屋に真上向きに置いた機械いもむしが上下に跳ねている
 ・縮小して置いたドッスンは最初から乗れる台（近道）
 ・棚の真上が棘になっている場所が2箇所ある
 ・最後のゲートは、箱を拡大して重量スイッチに乗せると開く


2-8. 跳ね回る敵（機械いもむし）

比較的新しく足した敵で、動きが目立つので聞かれることがあります。

  タイプ番号   22（Bouncing Worm）
  動き         重力を受けずに向いている方向へまっすぐ飛び続け、
               壁・床・天井に当たるとランダムな角度で跳ね返る
  胴体         頭の通った跡を節が辿る。既定6節

調整できる項目は、飛ぶ速さ（既定3.0 px/フレーム）、
跳ね返り角の乱れ（既定25度、0にすると物理どおりの正反射）、
胴体の節の間隔（既定22px）です。節の数はパーツ編集で増減します。

編集への反応は、回転すると回した向きがそのまま進む方向になり、
反転で逆向き、拡大で遅く、縮小で速くなります。
ステージに置くときの角度も、そのまま飛び出す方向になります。

跳ね返り角の決め方は4-3で説明する決定論の話に直結します。


2-9. ステージの進行とセーブ

  画面遷移     タイトル ⇄ ステージ選択 → プレイ ⇄ リザルト
  セーブ先     %LOCALAPPDATA%\LabProject01\save.json
  保存内容     クリアしたステージと、そこで取ったアイテムの最高数

ステージごとに解放条件を設定できます。
「常に選べる」「前のステージをクリア」「指定ステージを全てクリア」の3種です。
同梱7本は1本目が「常に選べる」、残りが「前のステージをクリア」です。

引数なしで起動するとタイトルから始まり、
コマンドライン引数でステージファイル名を渡すと
タイトルを飛ばして直接そのステージへ入ります。
Lab_Editor のテストプレイはこの引数付き起動を使っています。


============================================================
3. システム構成
============================================================

3-1. 3つの箱と、一方向のデータの流れ

  Lab_Editor (C#/.NET 8) ──書く──▶ assets/*.json ──読む──▶ ゲーム本体 (C++/DxLib)
   ステージ・アセット編集            敵/ギミック/アイテム        実行・物理・描画
   ブロックエディタ                  タイル/ステージ/音          巻き戻し・編集ツール
   パーツ合成エディタ                タイトル画面/セーブ要件
       ▲                                                        │
       └────────── プレイ でプロセス起動、遊んで確認 ──────────┘

押さえておく事実

 ・エディタはゲームランタイムを持っていません。
   物理も当たり判定も持たず、JSON を書くだけです。
 ・逆に、ゲーム本体はエディタを知りません。JSON を読むだけです。
 ・両者をつなぐのは assets/ 以下の JSON だけです。
   片方を直しても、もう片方をビルドし直す必要はありません。

唯一の例外がパーツ再生プレビュー用の ScriptPreviewEvaluator.cs（159行）です。
これは C++ 側インタプリタの再実装ではなく、
SetLocalOffset 系だけを見る近似評価器だとコード冒頭に明記してあります
（Lab_Editor/Lab_Editor/ScriptPreviewEvaluator.cs:10）。


3-2. データ駆動の境界線

聞かれたときに線を引けるように、両側を覚えておくとよい部分です。
一言でいえば「語彙を増やすのが C++、語彙を組み合わせるのが JSON」です。

C++ の再ビルドが必要になるのは4つだけ

 ・新しい type_enum（ネイティブな敵AI・ギミックの新種）を足すとき
 ・新しいブロック命令（op）を足すとき
 ・編集リアクションの新しい effect 名を足すとき
 ・スクリプトから読める状態を増やすとき

JSON だけでできること

 ・既存の型のパラメータを変えて別物を作る
 ・ブロックを組み合わせて完全に新しい挙動を書く（type 20 / 24）
 ・敵、ギミック、アイテム、タイルの定義
 ・複合パーツの組み立て
 ・ステージ、背景、音、タイトル画面、ステージ一覧、セーブの解放条件
 ・編集コストの数値、ステージごとの使える編集ツール

つまり同じ型から複数の別物を作る、というデータ駆動の使われ方が
実際に起きています。

後方互換の作りも一緒に説明できます。

既存の JSON を1文字も変えずに済みました。

4-1. ゲームループと画面

  内部解像度     640 × 480
  ウィンドウ     1280 × 720（内部解像度から拡大して合成）
  フレームレート 60fps（DxLib の ScreenFlip による垂直同期）

エディタUI表示中は、640×480 のゲーム画面がモニタ風の枠の中に置かれ、
周囲に左パネル、右インスペクタ、下部タイムラインが配置されます。
その枠内の左上は (320, 80)、大きさは 640×480 です（DrawPixel.cpp:3614）。

ゲームロジックはすべて 1/60 秒を1フレームとして固定計算しています。
重力の 0.5 などもフレーム単位の値です。

シーンは5つです（DrawPixel.cpp:1246）。

  PLAY / RESULT_GAMEOVER / RESULT_VICTORY / TITLE / STAGE_SELECT

TITLE と STAGE_SELECT はループ先頭で早期 continue し、
ゲームプレイ本体（約4500行）を丸ごと飛ばします。
条件式であちこちを潰す方式にすると、シーンを足すたびに
全判定箇所を直す必要が出るためです（DrawPixel.cpp:4775 のコメント）。

ステージのリセットは ResetStage() 1箇所に集約されています。
起動時・ステージ切替・死亡・リトライの全経路が必ずここを通ります。


4-2. 巻き戻しの実装とメモリ

  保持する長さ   600フレーム＝10秒（DrawPixel.cpp:1288）
  データ構造     リングバッファではなく std::vector を FIFO として使う
  読み出し       back() を読んで pop_back() する破壊的な消費

つまり巻き戻した分の履歴は消え、再び前進すると記録し直されます。
記録は「そのフレームに実際に更新が走ったとき」だけなので、
ポーズ中や編集ドラッグ中は履歴が伸びません。

設計上の肝は、敵の履歴が座標だけでなく AI の内部状態まで持っていることです
（struct EnemyState、DrawPixel.cpp:1350）。
customTimer、aiState、patrolLeft、patrolRight、auxF1〜3 といった
状態機械の変数まで記録しています。
ここを省くと、巻き戻した敵が「位置は過去なのに、頭の中は未来のまま」になります。

1フレームあたりの記録サイズと、600フレームぶんの量

  PlayerState    44 B    約 26 KB
  EnemyState     80 B    約 48 KB / 1体
  BulletState    20 B    約 12 KB / 1発
  GimmickState   16 B    約 9.6 KB
  ItemState      12 B    約 7.2 KB

弾は40発の固定プールです（DrawPixel.cpp:1200）。
つまり配置数に関係なく常時 480 KB を占めます。

敵10体、ギミック20個、アイテム10個のステージで、合計おおよそ 1.25 MB。
これが「巻き戻しにどれくらいメモリを使うか」への答えになります。

巻き戻しが波及する先

 ・壊したタイルは、壊れてからの経過フレームが巻き戻り、0で元に戻る
 ・巻き戻し中の敵は過去の残像あつかいで、すり抜けられる。
   頭上に PHASE と表示される
 ・一時停止中の敵は頭上に STAND と表示され、足場になる
 ・幽霊タイプの敵は、プレイヤーの履歴を遅延再生して過去の動きをなぞる。
   遅延フレーム数は編集で変わる（拡大で古い過去へ、縮小で迫ってくる、
   反転で軌跡を左右鏡像で再生）
 ・機械いもむしの胴体は専用バッファを持たず、巻き戻し履歴を軌跡として使う


4-3. 決定論性

機械いもむしの跳ね返り角には rand() を使っていません。
代わりに「何回目の跳ね返りか」と「どこで跳ね返ったか」だけから
ハッシュを作ります（BounceJitterUnit()、DrawPixel.cpp:1829）。

  unsigned int h = (bounceIndex + 1) * 2654435761u;
  h ^= (unsigned int)(seedX * 16.0f) * 40503u;
  h ^= (unsigned int)(seedY * 16.0f) * 2246822519u;
  h ^= h >> 13; h *= 1274126177u; h ^= h >> 16;
  return ((float)(h & 0xFFFFu) / 32767.5f) - 1.0f;   // -1.0〜1.0

跳ね返り回数も座標も履歴に入っているので、
何度巻き戻して再生しても必ず同じ角度になります。

理由はコードのコメントにそのまま書いてあります。

  巻き戻して同じ場面をもう一度再生したときに軌道が変わってしまうと、
  「巻き戻して跳ね返り先を見てから動く」という遊び方そのものが
  成立しなくなる。

遊びの要件が実装の制約を決めた例として使えます。

正確に言うべき点として、rand() は2箇所に残っています。
テレポート敵の転移先（DrawPixel.cpp:7346）と、
暗転させる敵の照準の揺れ（DrawPixel.cpp:7181）です。
跳ね返り系は完全に決定論、テレポート系は未対応、という状態です。


4-4. 「編集は巻き戻らない」という統一ルール

巻き戻すのは位置・速度・生死だけで、
傾けた角度や広げた幅はそのまま残る、と決めてあります。

実装は「現在値だけでなく、履歴配列を丸ごと書き換える」という形です。

  for (auto& h : e->history) { h.x += dx; h.y += dy; }   // 移動 DrawPixel.cpp:5601
  for (auto& h : e->history) { h.scale = e->scale;   }   // 拡大 DrawPixel.cpp:5621
  for (auto& h : e->history) { h.angle = e->angle;   }   // 回転 DrawPixel.cpp:5665

理由は DrawPixel.cpp:5583 のコメントにあります。
軸ごとにバラバラな挙動（傾けた直後に巻き戻すと角度だけ戻る、
幅は履歴に無いので残る）になると、
プレイヤーから見て何が保存され何が戻るのか読めなくなるためです。


4-5. ブロックスクリプト処理系（BehaviorScript.h）

型番号20（敵）と24（ギミック）は「カスタムスクリプト」で、
挙動が JSON の木として定義されます。パーツ単位でも持てます。

実装方式

 ・JSON AST をそのままツリーウォークで実行します。
   バイトコードへのコンパイルはしません。
   理由は BehaviorScript.h:18 に2つ書いてあります。
   エディタが保存した JSON をそのまま食わせられること、
   単一ヘッダで完結して再コンパイルが要らないことです。
 ・用語の言い換え：ツリーウォーク型インタプリタとは、
   組み上げたブロックの木を、実行時にそのまま辿って動かす方式のこと。
 ・インタプリタは Enemy も Gimmick も知りません。ScriptActor という
   ポインタを並べた構造体1枚だけでつながっています（BehaviorScript.h:106）。
   弾の生成や効果音の再生は std::function で外から注入します。

フレームを跨いで再開する方式

C++ のコールスタックは使わず、自前の std::vector<ScriptFrame> に積みます
（BehaviorScript.h:183）。ScriptFrame は
「実行中のブロック列」「プログラムカウンタ」「ループの種類」を持ち、
通常のブロック列・Forever・Repeat(N)・RepeatUntil の4種類を
1つの構造体で表します。中断した位置から次フレームで再開できます。

無限ループでフリーズしない仕組み（4段）

  1体・1フレームあたりの命令数        500     BehaviorScript.h:219
  全スクリプト合計・1フレームあたり   20000   同上
  コールスタックの深さ                32      同上
  超えたら Faulted 状態にして
  そのスクリプトだけ停止（ゲームは継続）      BehaviorScript.h:323

本命は4つ目ではなく、ループ境界の扱いです。
Forever / Repeat / RepeatUntil は、1周してループの先頭に戻る瞬間に
必ずそのフレームの実行を打ち切ります（BehaviorScript.h:281）。
つまり「1周＝1フレーム」が保証されるので、
Wait を1つも書かない Forever でも固まりません。
Scratch のセマンティクスをそのまま安全装置に転用した形です。

壊れたスクリプトを積んだ敵は、デバッグモードでなくても
頭上に赤字で SCRIPT ERROR が出ます（DrawPixel.cpp:9683）。

命令セットは73種

  数値を返すブロック   30種  SelfX, PlayerX, DistanceToPlayer, Random,
                             Sin, Cos, Time, ParentX, PartIndex,
                             EditScaleRatio, EditTilt など
  真偽を返すブロック   16種  Gt, Lt, And, Not, IsGrounded, IsWallAhead,
                             EditFlipped, EditPaused, IsFastForward など
  実行ブロック         24種  Forever, Repeat, If, Wait, MoveDirection,
                             SetLocalOffset, SetAngle, Shoot, PlaySound,
                             SetVar など
  開始ブロック          3種  OnSpawn, OnDamaged, OnDeath

C# エディタ側のカタログ（BlockDef.cs）も73個で、完全に一致しています。

時計は2種類あります。ポーズ中も進む globalFrameCounter と、
ポーズ中は止まる scriptTimeCounter です。分けてある理由は、
ポーズ解除直後に Time 依存の回転パーツが不連続にジャンプしないようにするためです。


4-6. 編集リアクションの3階建て

「拡大されたら重くなる」「傾けたら滑る」といった反応を3層に分けています。
下ほど汎用で、上が下を上書きするのではなく、追加で覆う形です。

  3階  型ごとの C++ 固有リアクション        C++ を書く必要がある
  2階  edit_reactions の JSON 宣言層        JSON だけで足せる
  1階  全オブジェクトに無条件で効く共通層  何もしなくても付く

設計意図が DrawPixel.cpp:2286 に明記されています。
新しい敵を足すとまず共通層の反応が自動で付き、足りなければ2階で味付けし、
それでも足りないときだけ3階を書く、という拡張コストの階段になっています。

共通層の中身は struct EditReaction（DrawPixel.cpp:1888）で、
「配置時からどれだけ手を加えたか」を正規化した差分を持ちます。
判定は原則ステートレスです（DrawPixel.cpp:1809）。
scale / angle / direction は巻き戻し履歴に入っているので、
余計な状態を足さなくても巻き戻しと自然に整合します。

しきい値は1箇所に集めてあります。
拡大縮小の検知は0.15、傾きは約11.5度、45度以上で「倒れた」あつかい、
60度刻みで離散的な段数を数える、といった値です。

スクリプト層はこの3階建てとは別の4本目の経路です。
FillScriptEditContext()（DrawPixel.cpp:2530）という1関数を必ず通して、
編集の差分を EditScaleRatio、EditTilt、EditFlipped などのブロックへ渡します。
敵本体、敵のパーツ、ギミック本体、ギミックのパーツの4箇所から呼ばれます。

正確に言うべき点として、2階の JSON 宣言層を実際に使っているアセットは
現時点で0件です。反応はすべて1階と3階で書かれています。
仕組みとしては完成していますが、使われるのはこれから、という状態です。


4-7. 「編集した事実」と「値が違う事実」を区別する

実際に踏んだ不具合の話で、切り分けの例として使えます。

EditReaction::flipped の中身は「今の向きが配置時と違う」でしかありません。
ところが、プレイヤーを追って自分から向きを変える敵では、
プレイヤーが左右を行き来するだけで真になってしまいます。

これが原因で、砲台の「反転させると味方撃ちになる」という反応が、
プレイヤーの立ち位置だけで弾の所属が入れ替わる状態になっていました
（DrawPixel.cpp:6266 にその記録が残っています）。
歩行・追跡・浮遊タイプの「反転で逃走」も、毎フレーム点滅して
事実上機能していませんでした。

対処は、「プレイヤーが編集した」という事実を別に持つことでした。
EditDirtyBits（DrawPixel.cpp:1339）という7本のビットフラグを用意し、
反転ツールを使ったかどうかは editDirtyMask & EDIT_DIRTY_DIR で見ます。

一般化すると「結果として値が違う」と「人が操作した」は別物である、
という話になります。


4-8. 複合パーツの親子変換

1体の敵を複数の画像パーツで組み立てられます。
ドッスンの黒目、砲台の砲身、ファイアバーの火の玉、多節の胴体などです。
パーツごとに個別の当たり判定とHPを持てます。

  HPが0のパーツ    破壊不能な常在ハザード。触れると常にダメージ
  HPが1以上のパーツ 弾で個別に破壊可能。破壊されても本体の生死には影響しない

パーツは親の移動・拡大・回転にすべて追従します。
親を2倍にすればパーツも2倍になり、中心からの位置関係も2倍に広がります。
継承する倍率は 0.25〜4.0 倍にクランプしてあります。
当たり判定が8×8しかないファイアバーを目一杯引き伸ばしたときに、
腕だけ画面外まで伸びる事故を防ぐためです。

実装上の要点

最初の不具合は「オフセットに倍率を掛け忘れ」ではなく、ピボットのズレでした。
親本体は「アンカー＋現在サイズ/2」を中心に描かれ、
パーツは「パーツ座標＋パーツサイズ/2」を中心に描かれます。
等倍では偶然一致しますが、2倍にすると親の中心だけが動きます。
オフセットが0なので、そこに何を掛けても直りません。

そこで「親中心をピボットにしてパーツ中心を動かす」形で
変換を定義し直しました（導出は BehaviorScript.h:29 に記号付きであります）。

  v     = L + h - Q                    // 親中心 → パーツ中心
  v'    = Rot(θ) * (v.x*sx, v.y*sy)
  world = P + (Q.x*sx, Q.y*sy) + v' - h*u

sx = sy = u = 1, θ = 0 を入れると P + L に還元されます。
つまり編集していない限り、既存のパーツ座標は1pxも変わらないことが
数式で保証されます（BehaviorScript.h:61）。
回帰が無いことは、全パーツ座標の CSV ダンプ差分で実証しました。

後方互換を、テストではなく恒等式で保証した例として使えます。

親が傾いてもプレイヤーを向き続けてほしいパーツ
（ドッスンの黒目、砲台の砲身など）は、
狙った角度から ParentTilt を引いて親の回転を打ち消します。


4-9. 当たり判定と物理

判定はすべて軸平行の矩形（AABB）です。

タイルマップとの判定は「軸分離＋セル走査」方式です。
X方向に動かして押し戻し、次にY方向に動かして押し戻す、という順で、
角に引っかからない標準的な実装になっています。

  x += dx;
  CheckGridCollisionX(...);      // 地形タイル
  CheckGimmickCollisionX(...);   // ギミック
  y += dy;
  CheckGridCollisionY(...);
  CheckGimmickCollisionY(...);
  （統括は UpdatePhysicsCollisions、DrawPixel.cpp:2852）

タイルは1マス32pxです。走査は (int)(x / 32) で開始セルと終了セルを出し、
矩形範囲をなめる形です。

例外が機械いもむしで、この敵は押し戻しではなく反射が必要なので、
「その位置へ行けるか」だけを判定する専用のヘルパーを使っています。

一時停止した敵を足場として扱う専用の判定もあります
（CheckFrozenEnemyPlatform、DrawPixel.cpp:2550）。
これは敵同士にも適用されます。

描画順は次のとおりです。

  背景レイヤー（視差スクロール、drawOrder の昇順）
  → 装飾タイル（奥）→ 当たり判定タイル → 装飾タイル（手前）
  → アイテム → ギミック → 敵 → プレイヤー → 弾
  → 画面エフェクト（明度・色調・ズーム）を掛けて 1280×720 へ拡大
  → エディタUI → ImGui


4-10. 敵とギミックで実装方式が違う

  敵      enum EnemyType 23種。switch(enemy.type) 一本で約1,600行
          （DrawPixel.cpp:6280 から）
  ギミック enum GimmickType 26種。責務ごとに分散した if/else
          更新は 8458〜8800、描画は 9356〜9680、
          足場になるかの判定は 2607、壁になるかの判定は 2785

この非対称は意図した設計ではありません。
理由を説明するなら、ギミックは「どの局面に参加するか」が型ごとに違う
（足場になる型、壁になる型、当たると即死する型、画面効果を出す型）ため、
1箇所にまとめきれず分散した、という経緯になります。

どちらも型番号の最後のひとつがカスタムスクリプトです。
敵は20、ギミックは24です。


4-11. トリガーイベント（EventManager.h）

RPGツクールのコモンイベントに相当する仕組みが実装されています。

  条件 6種    PlayerEnter（矩形に入っている間）
              PlayerExit（出た瞬間）
              AllEnemiesDefeated（残敵0）
              SwitchOn（指定スイッチがON）
              ItemCollected（アイテム取得）
              TimerExpired（経過秒数超過）

  アクション 12種  ShowMessage, ChangeBgm, PlaySe, ActivateGimmick,
                   OpenDoor, SpawnEnemy, SpawnItem, SetSwitch,
                   MoveCamera, StageClear, GoToStage, CallCommonEvent

CallCommonEvent は再帰実行に対応しており、
コモンイベントの中からさらにコモンイベントを呼べます。
アクションには遅延秒数を設定できます。

ただし、同梱7ステージの triggers は全て0件で、
common_events.json も空です。エンジンとエディタUIは完成していますが、
現在のコンテンツでは使っていません（9章参照）。

  当たり判定エディタ 画像の上で矩形をドラッグして調整
  サイズエディタ   プリセット、仕上がり幅[px]、倍率、ハンドルドラッグの4通り
  タイル定義       色、当たり判定、即死判定、画像の切り出し範囲、破壊条件
  アニメーション   スプライトシートのコマ割り
  サウンド管理     BGM/SE のカタログ登録と、場面への割り当て
  背景設定         視差スクロールのレイヤー、プレビュー付き
  ゲーム設定       タイトル画面の配置、ステージ一覧、解放条件、効果音の割り当て
  配布パッケージ   zip を作る

テストプレイは2通りあります。
F5 で現在のステージを頭から、または「ここからプレイ」で
マップ上の好きな位置をクリックしてそこから始められます。
後者は開始位置だけ差し替えた _test_play.json を別に書き出すので、
本来のステージファイルは上書きされません。


5-2. Scratch風ブロックエディタの実装

7ファイル、合計約1,900行です。責務がはっきり分かれています。

  BlockDef.cs               ブロックの種類カタログ（73種）
  BlockInstance.cs          置かれたブロック1個と、ドラッグの運搬データ
  BlockLayout.cs            2パスで寸法と座標を決める
  BlockRenderer.cs          GDI+ で見た目を描くだけ
  BlockPaletteControl.cs    パレット（検索、ツールチップ、ドラッグ元）
  BlockCanvasControl.cs     組み立てキャンバス
  BlockScriptSerializer.cs  ツリー と JSON AST の相互変換

レイアウトは2パスです（BlockLayout.cs:4）。
Measure が子から親へ寸法を確定し、Arrange が親から子へ座標を確定します。
キャッシュも差分更新もせず毎回全部計算しますが、
ブロック数が数百に達する想定ではないので十分だとコメントにあります。

描画は GDI+ です。完全なジグソー型の輪郭は描かず、
ヘッダ・背骨・フッタの重ね合わせで簡略表現しています。
下側の凹はキャンバスの背景色で塗るトリックを使っています。

ドラッグ＆ドロップは OS の DoDragDrop です。
掴んだブロック以降をまとめて持ち上げる（Scratch と同じ挙動）、
ソケットは型で厳格に弾く（数値欄にはピル型だけ、条件欄には六角形だけ）、
自分の中に自分を落とせないよう子孫を除外する、といった作りです。
ドロップに失敗したときは元の位置へ戻します。

Ctrl + ホイールでズームできますが、
レイアウト計算と当たり判定は常に等倍の論理座標で行い、
描画とマウス座標の変換だけをズーム率で補正しています。

JSON AST の形式は次のとおりです。

  [ { "hat": "OnSpawn", "body": [
        { "op": "Forever", "body": [
            { "op": "MoveDirection", "dir": "Toward", "speed": 2 },
            { "op": "Wait", "frames": 30 }
        ] }
  ] } ]

引数は op と同階層のフラットなキーです。
ソケットにブロックが差さっている場合は、その引数キーの値がオブジェクトになります。

運用上の注意がコードに書かれています（BlockDef.cs:261）。
カタログに未登録の op は、シリアライザが読み飛ばして保存時に無言で消えます。
エンジンに op を足したら必ずカタログにも足す、という決まりです。

プログラミング未経験者向けにテンプレートが6種入っています。
左右パトロール、近づいたら追いかける、一定間隔で狙撃、
上下に振動する床、その場で回転し続ける、被弾時に一瞬無敵＋点滅です。


5-3. パーツエディタと自動生成

画面は3分割で、左がパーツ一覧、中央が合成プレビュー、
右が選択中パーツの詳細です。中央ではパーツを直接ドラッグして
初期位置を調整できます。約16ミリ秒間隔のタイマーで、実機と同じ速さで
スクリプトを再生プレビューできます。

「回転する棒として配置」というウィザードがあります。
マリオのファイアバーのような、一直線に並んだまま回る棒を一括生成します。

仕組みとしては、全パーツに同一の JSON AST を割り当て、
半径だけを PartIndex（自分が何番目のパーツか）から決めています。

  角度   Time × 速さ           （全パーツ共通）
  半径   (PartIndex + 1) × 間隔 （ここで個体差が出る）
  命令   SetLocalOffsetPolar(angle, radius) を Forever で回す

つまり手でも組める AST を、ウィザードがプログラム的に組み立てているだけです。
しかも生成済みのスクリプトを逆解析して、
同じ仲間をまとめて検出し、パラメータを変えて再生成できます。

姉妹機能として「振り子」と「公転」があります。
公転との違いは、公転は半径が一定で角度が PartIndex ごとにずれるのに対し、
回転する棒は角度が共通で半径が PartIndex ごとにずれる点です。


5-4. UI構造の作り直し

改修前は、アセット管理 → パーツ編集 → 挙動スクリプト編集 と、
最大3重に ShowDialog() が積み重なっていました。
ダイアログの上にダイアログが開き、戻るのも
「ウィンドウを閉じる」の繰り返しでした。

これをパンくず付きの単一ウィンドウのページ遷移に置き換えました
（WorkbenchShellForm.cs）。

その痕跡が、〜Form.cs（薄いラッパー）と 〜PageControl.cs（実体）の対です。
中身を UserControl に抽出し、結果を Saved / Cancelled イベントで返すように
したので、呼ぶ側が「モーダルで開く」か「シェル内でページ遷移する」かを
選べます。旧来の呼び出し元を壊さないために Form 側を残してあります。

対になっているのは7組です。AssetManager、PartsEditor、
BehaviorScriptEditor、HitboxEditor、SizeEditor、CommonEventEditor、
GameConfig です。


5-5. 保存とUndo

タイマーによる自動保存はありません。
「一連の編集操作が終わった」というイベントごとに、
保存と Undo スナップショットを同時に行います（Form1.cs:660）。
そのため保存し忘れが構造的に起きません。

Undo は JSON往復のスナップショット方式です。
状態をそのまま持つのではなく、一度 JSON 文字列にしてから積み、
戻すときに復元し直します。
参照の使い回しによる意図しない書き換えが起きません。上限は50件。

コマンドパターンではないので実装は単純で漏れがない代わりに、
メモリは「状態のサイズ × 50」を使います。


5-6. ゲーム本体の起動

Lab_Editor が起動する exe は、x64/Debug と x64/Release のうち
後からビルドされた方を、タイムスタンプ比較で自動的に選びます
（Form1.cs:884）。どちらが選ばれているかは画面下のステータスバーに出ます。

起動は3通りです。

  F5              現在のステージを引数で渡して起動
  Shift + F5      引数なしで起動し、タイトル画面から確認できる
  ここからプレイ  開始位置を差し替えた _test_play.json を書き出して起動

ゲーム側は「コマンドライン引数が付いているか」だけで
エディタからのテストプレイかどうかを判断しています。


5-7. データモデル層

StageData.cs（1,174行、21の型）がエディタと C++ 本体をつなぐ共有スキーマです。

全クラスに JsonExtensionData を付けてあります。
これは「C++ 側と1対1で対応させないと、ここに無いキーは
エディタで保存し直した瞬間に黙って消える」という地雷への対処です。
未知のキーを拾って書き戻すので、
C++ 側だけが解釈するキーを後から足してもエディタを通して消えません。

game_config.json のデータモデルだけは別ファイルに分けてあります。
アセット定義の保存処理は呼ばれるたびに9本の JSON を全部書き直すため、
そこに混ぜると「敵の当たり判定を直そうとしてアセット管理を保存しただけなのに、
タイトル画面のレイアウトも書き直された」が起きるためです。

6-2. 配布の仕組み

zip を展開して exe をダブルクリックするだけで動きます。
Lab_Editor は同梱していません（.NET ランタイムが別途必要になるためと、
開発用ツールであるため）。

配布可能にするまでの経緯が、説明として使える部分です。

アセットの参照は全てカレントディレクトリからの相対パスで、約67箇所あります。
動いていたのは Lab_Editor が作業ディレクトリを指定して起動していたからで、
ゲーム単体では配布できない状態でした。

「パス解決関数を作って67箇所を包む」案を採らなかった理由が
GamePaths.h:8 に2つ書いてあります。

 1. 67箇所のうち10箇所は JSON 由来の変数パスで、
    包み忘れてもコンパイルが通ります。
    1箇所でも漏らすと「配布版でだけ特定の敵が見えない」という
    最悪の壊れ方をします。
 2. 文字コード。リテラルは UTF-8 バイト列なので、
    exe のパス（CP932）とナロー文字列で連結すると混在して壊れます。

採った方法は、exe の場所から最大8階層まで親を遡って
assets/enemies.json を探し、見つかった場所へ
カレントディレクトリを移すというものです（GamePaths.h:37, GamePaths.h:53）。
書き換えは0箇所で、開発フォルダでも配布フォルダでも同じバイナリが動きます。

セーブデータは %LOCALAPPDATA%\LabProject01\ に置くので、
Program Files の下へ入れても権限エラーになりません。

配布物を作る入口は2つあり、どちらも同じ tools/build_dist.ps1 を呼びます。
Lab_Editor のメニュー「ファイル」→「配布用パッケージを作る」か、
build_dist.bat のダブルクリックです。

署名を付けていないので、起動時に
「Windows によって PC が保護されました」が出ます。
これは署名の無いソフト全てに出るもので、
「詳細情報」→「実行」で起動できます。

============================================================
8. 設計判断と、その理由
============================================================

「なぜそうしたのか」を問われたときに答えられるよう、
判断とその根拠を並べてあります。


8-1. なぜ Unity ではなく DxLib + 自作か

DxLib が提供するのは描画・入力・音の3つだけです。
ゲームループ、状態管理、当たり判定、更新順序、履歴の持ち方は
すべて自分で書く必要があり、逆に言えばすべて自分で決められます。

このゲームの中心は「プレイ中に時間とオブジェクトを編集する」ことなので、
次のような設計を素直に入れられることが要件でした。

 ・敵の履歴に AI の状態機械まで含める
 ・巻き戻し中は当たり判定を切る
 ・編集した値は巻き戻しの対象から外す
 ・更新順序を変えて、プレイヤーの画面効果を敵の演出より後に適用する

既製エンジンの上に乗せると、これらは既にある仕組みの上に
重ねる形になります。学習環境として日本語の情報が多いことも選択の理由です。


8-2. なぜ C++ と C# を混ぜたか

ゲーム本体は毎フレーム数百のオブジェクトを回すので C++。
エディタはウィンドウ、ツリー、ドラッグ＆ドロップを大量に作るので C# WinForms。
向いている道具が違います。

つなぎが JSON だけなので、片方を直しても
もう片方をビルドし直す必要がありません。


8-3. なぜカットのコストを距離に比例させたか

カットは「ステージの一区間を丸ごと飛ばす」最も強い操作です。
最初は長さに関係なく定額でした。その結果、
「ゲージが溜まったら端から端まで1本引いて丸ごと飛ばす」のが
常に最適解になっていました。

20 + 1.2 × 飛ばすタイル数 に変えたことで、
短いカットは安くて細かく使え、長いカットはゲージを使い切る
覚悟の一手になりました。「どこをどれだけ飛ばすか」自体が
考えどころになった、というのが狙いどおりだった部分です。

cutCostPerTile を0にすれば従来の定額へ戻せるので、後方互換も残してあります。


8-4. なぜ編集にコストを付けたか、なぜドラッグだけ無料か

コストが無いと、詰まったら片っ端から編集すれば済んでしまいます。
逆に全ての操作に課金すると、試すこと自体が怖くなって手が止まります。

その折り合いとして、右クリックメニュー経由の操作にはコストを掛け、
ドラッグでの変形（移動・拡大縮小・回転）は無料にしてあります。
一時停止の解除と、色フィルタを「なし」に戻す遷移も無料です。


8-5. なぜ難易度ではなく道具の数で調整したか

ステージごとに使える編集ツールを絞れるようにしてあります。
後半3本は2つずつしか使えません。

道具が少ないほど解き方が一本道になるので、
「何をすればいいか分からない」ではなく「どう使うか」を考える形になります。
道具が全部あると、組み合わせが多すぎて逆に手が止まります。


8-6. なぜ「編集は巻き戻らない」と決めたか

軸ごとにバラバラな挙動（傾けた直後に巻き戻すと角度だけ戻る、
幅は履歴に無いので残る）になると、
プレイヤーから見て何が保存され何が戻るのか読めなくなります。

「巻き戻すのは位置・速度・生死だけ、編集した形はそのまま残る」
という一貫したルールに統一しました。
時間を戻しても自分がやった改造は残る、という理解しやすい形になります。


8-7. なぜバイトコードにコンパイルせず JSON を直接実行するか

エディタが保存した JSON をそのまま食わせられることと、
単一ヘッダで完結して再コンパイルが要らないことの2つが理由です
（BehaviorScript.h:18）。

性能面では、1体あたり1フレーム500命令という上限があり、
そこまで回すスクリプトは想定していないので問題になっていません。


8-8. なぜ乱数を使わないか

「巻き戻して跳ね返り先を見てから動く」という遊び方を成立させるためです。
巻き戻して同じ場面を再生したときに軌道が変わると、
確かめてから動くという行為が意味を失います。

遊びの要件が実装の制約を決めた例になっています。


8-9. なぜ専用のエディタまで作ったか

タイルマップは1ステージで 100×15 マスあります。
当たり判定、パーツの位置、ブロックの組み立ては、
数値で書くより見ながら動かすほうが圧倒的に速く、間違いも減ります。

7月6日にエディタに着手して以降、開発の速度が明確に変わりました。


8-10. テストをどうしているか

自動テストは書いていません。
代わりに、直す前後で必ず差分が取れる形にしています。

 ・恒等式で保証する。複合パーツの親子変換は、編集していないときに
   数式が元の式へ還元されることを先に確かめてから実装しました。
   そのうえで全パーツ座標を CSV に落とし、変更前後で差分ゼロを確認しています。
 ・毎フレームの軌跡を CSV に落とす。終わった状態だけ見ても
   分からない不具合が多いので、1フレームごとの座標と速度を吐かせて見ます。


8-11. 11,000行の単一ファイルについて

DrawPixel.cpp は大きくなりすぎています。これは弱点として認めるところです。

現状の対処は、Feature ごとの見出しコメントと、
「なぜそうしたか」まで書いた日本語の設計コメントで引く、というものです。

そのうえで、意識的に外へ出した部分があります。
スクリプト処理系、イベント、音、設定とセーブ、パス解決の5つは
ヘッダに切り出してあり、どれもゲーム本体の型を知りません。
特にスクリプト処理系は Enemy も Gimmick も知らず、
ポインタを並べた構造体1枚だけでつながっています。


8-12. 実際に一番手こずった不具合

落ちてくる敵（ドッスン）が、一度落ちたきり戻ってこなくなる不具合です。

着地判定は「縦の速度がほぼ0なら着いた」という形で
abs(vy) < 0.5 と書いていました。
ところが重力は毎フレーム 0.5 足され、着地すると
当たり判定が vy を0に落とします。
つまり地面の上では vy が毎フレームちょうど 0.5 になります。
0.5 < 0.5 は偽なので、着地が永久に検出されませんでした。

終わった状態だけダンプしても分かりませんでした。
落下の大半は26フレームの「溜め」で終わり、
実際に落ちている時間が数フレームしかないためです。
毎フレームの軌跡を CSV に落として初めて、
重力が二重に掛かっていることに気づけました。

一般化すると「速度で状態遷移を判定してはいけない」。
速度は結果であって、状態ではありません。


8-13. AI の利用について

============================================================
9. 既知の制限と、まだ使っていない機能
============================================================

聞かれる前に自分から言えるようにしておくと、話が早くなります。


9-1. 制限

 ・巻き戻しはスクリプトの内部状態を戻しません。
   対象は位置・速度・向き・大きさ・角度・生死だけで、
   スクリプトの変数やコールスタック、パーツのHPは含まれません。
   スクリプトで動く敵を巻き戻すと、見た目の位置は戻っても
   内部状態は戻らない場合があります。
 ・OnDeath は死亡と同じフレーム内で完結する処理だけに対応しています。
   Wait を挟む複数フレームの死亡演出はできません。
 ・乱数が2箇所に残っています。テレポート敵の転移先と、
   暗転させる敵の照準の揺れです。この2つは巻き戻し再現性が崩れます。
 ・アイテムは編集ツールの選択対象になっていません。
   編集禁止フラグの欄はありますが、まだ効果がありません。
 ・当たり判定は常に軸平行の矩形です。パーツの回転角は判定に反映されません。
 ・Windows 専用です。DxLib が DirectX のラッパーであるためです。
   ただしアセットは全て JSON と PNG と WAV なので、
   描画層を差し替えれば移植できる形にはなっています。
 ・一部のギミックに専用のスプライト画像が用意されておらず、
   汎用画像で代用しているものがあります。
 ・効果音の素材が足りていません。敵の攻撃音、被弾音などが未整備です。


9-2. 仕組みはあるが、同梱コンテンツでは使っていないもの

これを「使っている」と説明すると、見せてくださいと言われたときに困ります。
3つあります。

 ・スプライトアニメーション
   AnimationController.h（232行）は完成していますが、
   animations.json が空配列で、全アセットが静止画運用です。
 ・トリガーイベント
   条件6種とアクション12種、エディタUI（EventEditorForm など）も
   完成していますが、同梱7ステージの triggers は全て0件で、
   common_events.json も空です。
 ・編集リアクションの JSON 宣言層（3階建ての2階）
   仕組みは動きますが、edit_reactions を持つアセットは0件です。
   反応はすべて共通層と型別 C++ で書かれています。

いずれも「拡張のためのレールを先に敷いた状態」という位置づけです。

============================================================
10. 出展中の運用に必要な知識
============================================================

10-1. 起動と終了

  タイトルから始める   引数なしで Lab_Project_01.exe を起動
  特定のステージから   引数にステージのファイル名を渡す
  終了                 Esc（どの画面でも効く）
  エディタへ戻る       ゲーム中に矢印キー全押し（開発用の隠し操作）

Lab_Editor が起動する exe は Debug と Release の新しい方です。
どちらが選ばれているかは画面下のステータスバーに出ます。


10-2. セーブデータ

  場所     %LOCALAPPDATA%\LabProject01\save.json
  消し方   Lab_Editor →「ゲーム設定」→「その他」→「セーブデータを削除」

前の人の進行状況が残っていると、次の人が最初の面から始められません。
入れ替えのタイミングで消す運用にしてください。

ステージ選択のサムネイルは、解放済みのステージにしか出ません。
セーブを消した直後は1本目だけにサムネイルが出て、
残りは灰色の「？？？」になります。これは仕様です。


10-3. ステージ選択の表示

  グリッド  3列。7本なので3段目に1つだけ並ぶ
  表示      解放済みはサムネイル、ステージ名、CLEAR の有無、アイテム取得数
  未解放    灰色のブロックと「？ ？ ？」

サムネイルの実体は img/thumb_*.png です。
ステージを作り直したら撮り直してください。
ゲームをそのステージで起動して画面を撮るだけです。


10-4. トラブルへの対応

  進行不能になった              Esc で終了して起動し直す
  棘や穴で何度も死ぬ            ステージ選択から入り直せば最初から
  「Windows によって PC が保護されました」
                                署名の無いソフト全てに出る。
                                「詳細情報」→「実行」
  画像が表示されない            logs/error.log に読み込み結果が出ている。
                                起動時の "All core graphics loaded" を最初に見る
  音が鳴らない                  起動時に全ての効果音IDを照合して、
                                カタログに無いIDを logs/error.log へ出している
  スクリプトの敵が動かない      頭上に SCRIPT ERROR が出ていないか。
                                出ていれば logs/error.log に理由がある

============================================================
11. 数字を数え直すコマンド
============================================================

プロジェクトのルート（Lab_Project_01.vcxproj があるフォルダ）で実行します。
Git Bash / WSL 想定です。

  # コード行数（C++。json.hpp は外部ライブラリなので除く）
  wc -l DrawPixel.cpp BehaviorScript.h GameConfig.h EventManager.h \
        AnimationController.h SoundManager.h Logger.h GamePaths.h

  # Lab_Editor（C#）。ビルド生成物を除いた手書き分だけ
  find Lab_Editor -name "*.cs" -not -path "*/obj/*" -not -path "*/bin/*" | wc -l
  find Lab_Editor -name "*.cs" -not -path "*/obj/*" -not -path "*/bin/*" \
    -print0 | xargs -0 wc -l | tail -1

  # 型の数（2つの結果を足す）
  H="BehaviorScript.h EventManager.h GameConfig.h AnimationController.h \
     SoundManager.h Logger.h GamePaths.h"
  grep -hcE '^[[:space:]]*struct [A-Za-z_]+' DrawPixel.cpp $H
  grep -hcE '^[[:space:]]*enum '             DrawPixel.cpp $H

  # 敵の型の数（末尾の番兵 ENEMY_TYPE_COUNT は数に入れない）
  sed -n '/^enum EnemyType/,/^};/p' DrawPixel.cpp \
    | grep -oE '^\s+ENEMY_[A-Z_0-9]+' | grep -v TYPE_COUNT | wc -l

  # ギミックの型の数
  sed -n '/^enum GimmickType/,/^};/p' DrawPixel.cpp \
    | grep -cE '^\s+GIMMICK_[A-Z_0-9]+'

  # ブロック命令の数
  grep -c "new BlockDef(" Lab_Editor/Lab_Editor/BlockDef.cs

  # アセットの定義数
  for f in enemies gimmicks items tiles; do
    printf "%-10s " "$f"; grep -cE '^    "id"' assets/$f.json
  done

  # 素材の数（img の thumb_*.png 7枚はステージ選択のサムネイル）
  ls img/*.png | wc -l
  ls img/thumb_*.png | wc -l
  ls sound/ | wc -l
  ls se/    | wc -l

  # 開発期間とコミット数
  git rev-list --count HEAD
  git log --reverse --format="%ad" --date=short | head -1
  git log -1 --format="%ad" --date=short
  git shortlog -sn
