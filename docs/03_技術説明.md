# 技術説明（10〜15分）

作品名は **Editron**、副題は「2Dアクションゲームのためのゲームエンジン」。
`Lab Project 01` はリポジトリと実行ファイルの名前です（コード中の参照はこちらの名前で出てきます）。

「何を作ったか」ではなく **「どの問題を、どう切り分けたか」** の順に並べています。
各項目の末尾に `ファイル:行` を書いてあるので、その場で開いて見せられます。

---

## 0. 全体構成 ── 3つの箱と、一方向のデータの流れ

```
 Lab_Editor (C#/.NET 8) ──書く──▶ assets/*.json ──読む──▶ ゲーム本体 (C++/DxLib)
  ステージ・アセット編集            敵/ギミック/アイテム        実行・物理・描画
  ブロックエディタ                  タイル/ステージ/音          巻き戻し・編集ツール
  パーツ合成エディタ                タイトル画面/セーブ要件
      ▲                                                          │
      └────────── ▶プレイ でプロセス起動、遊んで確認 ──────────┘
```

**エディタはゲームランタイムを持ちません。** 物理も当たり判定も持たず、JSON を書くだけです。
唯一の例外がパーツ再生プレビュー用の `ScriptPreviewEvaluator.cs`（159行）ですが、
これは C++ 側インタプリタの再実装では**なく**、`SetLocalOffset` 系だけを見る近似評価器だと
コードに明記してあります（`Lab_Editor/Lab_Editor/ScriptPreviewEvaluator.cs:10`）。

同じ構造を `docs/img/全体構成図.svg` に描いてあります。

## 1. データ駆動の境界線 ──「語彙はC++、組み合わせはJSON」

よく聞かれるので、先に線を引いておきます。

| C++ の再ビルドが要る | JSON だけでできる |
|---|---|
| 新しい `type_enum`（ネイティブAIの新種） | 既存の型のパラメータを変えて別物を作る |
| 新しいブロック命令（op）を足す | ブロックを組み合わせて新しい挙動を書く |
| 新しい `effect` 名を足す | 敵・ギミック・アイテム・タイルの定義 |
| スクリプトから読める状態を増やす | ステージ・背景・音・タイトル画面・セーブ要件 |

**ギミックは36個の定義が26種類の型に分かれています。** 同じ型から複数の別物を作るという
データ駆動の使われ方が、実際に起きている証拠になります。

後方互換の作りも見せどころです。`ApplyEnemyDefaultParams()` は
「JSON で未設定（`-1`）のフィールドだけ、その型が従来ハードコードで使っていた値で埋める」
という形なので、**新しいパラメータを追加しても既存の JSON を1文字も変えずに済みます**
（`DrawPixel.cpp:468`）。

## 2. 巻き戻し ──「位置は過去、頭の中は未来」を避ける

10秒ぶん（600フレーム）を全オブジェクトについて持ちます（`DrawPixel.cpp:1288`）。
リングバッファではなく `std::vector` を FIFO として使い、
巻き戻しは `back()` を読んで `pop_back()` する**破壊的な消費**です（`DrawPixel.cpp:6170` 付近）。

**設計上の肝は、敵の履歴が座標だけでなく AI の内部状態まで持っていること**です
（`struct EnemyState`、`DrawPixel.cpp:1350`）。
`customTimer` / `aiState` / `patrolLeft` / `auxF1〜3` といった状態機械の変数まで記録しています。
ここを省くと、巻き戻した敵が「位置は過去なのに、頭の中は未来のまま」になります。

メモリの見積りも用意してあります。

| 構造体 | サイズ | 600フレームぶん |
|---|---|---|
| `PlayerState` | 44 B | 約 26 KB |
| `EnemyState` | 80 B | 約 48 KB／1体 |
| `BulletState` | 20 B | 約 12 KB／1発（**40発の固定プール**、`DrawPixel.cpp:1200`） |
| `GimmickState` | 16 B | 約 9.6 KB |
| `ItemState` | 12 B | 約 7.2 KB |

敵10体・ギミック20個・アイテム10個のステージで、**合計おおよそ 1.25 MB**。
そのうち 480 KB が弾のプールです。

## 3. 決定論性 ──「巻き戻して確かめてから動く」を成立させる要件

跳ね回る敵（機械いもむし）の跳ね返り角には、**`rand()` を使っていません**。
代わりに「何回目の跳ね返りか」と「どこで跳ね返ったか」だけからハッシュを作ります
（`BounceJitterUnit()`、`DrawPixel.cpp:1829`）。

理由がコードのコメントにそのまま書いてあります。

> 巻き戻して同じ場面をもう一度再生したときに軌道が変わってしまうと、
> 「巻き戻して跳ね返り先を見てから動く」という遊び方そのものが成立しなくなる。

**遊びの要件から実装の制約が決まった例**として話すのが効きます。
跳ね返り回数も座標も履歴に入っているので、何度再生しても必ず同じ角度になります。

胴体の節も専用バッファを持たず、**巻き戻し用の履歴をそのまま軌跡として使っています**
（`DrawPixel.cpp:8105`）。別のバッファを持つと、巻き戻したとき胴体だけ未来の形で残るためです。

**正直に言うこと**：`rand()` は2箇所に残っています。テレポート敵の転移先（`DrawPixel.cpp:7346`）と、
暗転させる敵の照準の揺れ（`DrawPixel.cpp:7181`）です。
「跳ね返り系は完全に決定論、テレポート系は今後の課題」と整理して答えます。

## 4. 「編集は巻き戻らない」という統一ルール

**巻き戻すのは位置・速度・生死だけ。傾けた角度や広げた幅はそのまま残ります。**

実装は「現在値だけでなく、履歴配列を丸ごと書き換える」という形です。

```cpp
for (auto& h : e->history) { h.x += dx; h.y += dy; }   // 移動 DrawPixel.cpp:5601
for (auto& h : e->history) { h.scale = e->scale;   }   // 拡大 DrawPixel.cpp:5621
for (auto& h : e->history) { h.angle = e->angle;   }   // 回転 DrawPixel.cpp:5665
```

理由は `DrawPixel.cpp:5583` のコメント。軸ごとにバラバラな挙動
（傾けた直後に巻き戻すと角度だけ戻る／幅は履歴に無いので残る）になると、
**プレイヤーから見て何が保存され何が戻るのか読めなくなる**ためです。

## 5. ブロックスクリプト ── JSON をそのまま実行する

エディタで組んだブロックは JSON の木になり、ゲーム側が**それを直接たどって実行**します。
バイトコードへのコンパイルはしません。理由は `BehaviorScript.h:18` に2つ書いてあります。

1. エディタが保存した JSON をそのまま食わせられる
2. 単一ヘッダで完結し、再コンパイルが要らない

> ツリーウォーク型インタプリタ
> ＝ 組み上げたブロックの木を、実行時にそのまま辿って動かす方式。

**インタプリタは `Enemy` も `Gimmick` も知りません。** `ScriptActor` という
ポインタを並べただけの構造体1枚でつながっています（`BehaviorScript.h:106`）。
弾の生成や効果音の再生は `std::function` で外から注入します。

### フレームを跨いで再開する

C++ のコールスタックは使わず、**自前の `std::vector<ScriptFrame>` に積みます**
（`BehaviorScript.h:183`）。通常のブロック列・`Forever`・`Repeat(N)`・`RepeatUntil` の
4種類を1つの構造体で表し、`pc`（プログラムカウンタ）を持たせて中断・再開します。

### 無限ループを書いてもフリーズしない（4段構え）

| 装置 | 値 | 場所 |
|---|---|---|
| 1体・1フレームあたりの命令数 | 500 | `BehaviorScript.h:219` |
| 全スクリプト合計・1フレームあたり | 20000 | 同上 |
| コールスタックの深さ | 32 | 同上 |
| 超えたら Faulted 状態にして**そのスクリプトだけ**停止 | — | `BehaviorScript.h:323` |

**本命は4つ目ではなく、ループ境界の扱いです。**
`Forever` / `Repeat` / `RepeatUntil` は、1周してループの先頭に戻る瞬間に
**必ずそのフレームの実行を打ち切ります**（`BehaviorScript.h:281`）。
つまり「1周＝1フレーム」が保証されるので、`Wait` を1つも書かない `Forever` でも固まりません。
Scratch のセマンティクスをそのまま安全装置に転用した形です。

壊れたスクリプトを積んだ敵は、デバッグモードでなくても
頭上に赤字で `SCRIPT ERROR` が出ます（`DrawPixel.cpp:9683`）。

## 6. 編集リアクション ── 拡張コストの3階建て

「拡大されたら重くなる」「傾けたら滑る」といった反応を、3層に分けています。
**下ほど汎用で、上が下を上書きするのではなく、追加で覆う**形です。

| 階 | 中身 | 拡張コスト |
|---|---|---|
| ③ | 型ごとの C++ 固有リアクション | C++ を書く |
| ② | `edit_reactions` の JSON 宣言層 | JSON だけ |
| ① | 全オブジェクトに無条件で効く共通層 | 何もしなくても付く |

設計意図が `DrawPixel.cpp:2286` に明記されています。
新しい敵を足すと**まず共通層の反応が自動で付き**、足りなければ②で味付けし、
それでも足りないときだけ③を書く、という順序で作れます。

共通層の中身は `struct EditReaction`（`DrawPixel.cpp:1888`）。
「配置時からどれだけ手を加えたか」を正規化した差分で、
**判定は原則ステートレス**です（`DrawPixel.cpp:1809`）。
scale / angle / direction は巻き戻し履歴に入っているので、
余計な状態を足さなくても**巻き戻しと自然に整合します**。

共通層だけで既に、こういう反応が全オブジェクトに付きます。

- 止めた敵は誰でも踏み台になる（`DrawPixel.cpp:2443`）
- 巻き戻し中の敵は過去の残像なのですり抜けられる（`DrawPixel.cpp:2466`）
- 拡大すると鈍く、縮小すると軽快になる（`MassMul()`）
- 暗いと索敵が狭まり、明るいと広がる

スクリプト層は**この3階建てとは別の4本目の経路**です。
`FillScriptEditContext()` という1関数を必ず通して、編集の差分を
`EditScaleRatio` / `EditTilt` / `EditFlipped` などのブロックへ渡します（`DrawPixel.cpp:2530`）。

> **正直に言うこと**：②の JSON 宣言層を実際に使っているアセットは、現時点で0件です。
> 反応はすべて①と③で書かれています。②は「これから増える敵のために先に敷いたレール」
> という位置づけで、仕組みとしては完成しています。

## 7. 「編集した事実」と「値が違う事実」を区別する

発表で一番受ける、実際のバグの話です。

`EditReaction::flipped` の中身は「**今の向きが配置時と違う**」でしかありません。
ところが、プレイヤーを追って自分から向きを変える敵では、
**プレイヤーが左右を行き来するだけで真になってしまいます**。

実際これが原因で、砲台の「反転させると味方撃ちになる」という反応が、
**プレイヤーの立ち位置だけで弾の所属が入れ替わる**状態になっていました
（`DrawPixel.cpp:6266`）。

直し方は、「プレイヤーが編集した」という事実を別に持つことです。
`EditDirtyBits`（`DrawPixel.cpp:1339`）という7本のビットフラグを用意し、
反転ツールを使ったかどうかは `editDirtyMask & EDIT_DIRTY_DIR` で見ます。

**「結果として値が違う」と「人が操作した」は別物**、という切り分けの話として使えます。

## 8. 編集コストゲージ ── カットの値段を距離で変えた理由

編集ツールはゲージを消費します（`struct EditCostSettings`、`DrawPixel.cpp:420`）。
継続系は毎秒、単発系は一括で引かれ、**ドラッグでの変形だけは無料**です。

| 操作 | 消費 |
|---|---|
| 巻き戻し（保持中） | 18.0 / 秒 |
| 早送り（保持中） | 10.0 / 秒 |
| 画面エフェクト（保持中） | 8.0 / 秒 |
| 一時停止（保持中） | 4.0 / 秒 |
| 自然回復（何も使っていない間） | 6.0 / 秒 |

ドレインは加算式なので、同時に使えば毎秒40まで膨らみます。
1つでも動いている間は回復しません（`DrawPixel.cpp:8825`）。

### 距離比例にした話

カットは「ステージの一区間を丸ごと飛ばす」最も強い操作です。
最初は長さに関係なく定額でした。その結果、
**「ゲージが溜まったら端から端まで1本引いて丸ごと飛ばす」のが常に最適解**になっていました。

そこで `20 + 1.2 × 飛ばすタイル数` に変えました（`ComputeCutCreateCost()`、`DrawPixel.cpp:1222`）。

- 短いカット … 安い。詰まった数マスを飛ばす、細かい使い方ができる
- 長いカット … 高い。ゲージを使い切る覚悟が要る、ここぞの一手になる

**「どこをどれだけ飛ばすか」自体が考えどころになりました。**
`cutCostPerTile` を0にすれば従来の定額へ戻せるので、後方互換も残してあります。

## 9. 複合パーツ ── 恒等変換を数式で保証してから実装した

1体の敵を複数の画像パーツで組み立てられます（ドッスンの黒目、砲台の砲身、
ファイアバーの火の玉、多節の胴体など）。パーツは親の移動・拡大・回転に追従します。

最初の不具合は「オフセットに倍率を掛け忘れ」ではなく、**ピボットのズレ**でした。
親本体は「アンカー＋現在サイズ/2」を中心に描かれ、パーツは「パーツ座標＋パーツサイズ/2」を
中心に描かれます。等倍では偶然一致しますが、2倍にすると親の中心だけが動きます。
**オフセットが0なので、そこに何を掛けても直りません。**

そこで「親中心をピボットにしてパーツ中心を動かす」形で変換を定義し直しました
（導出は `BehaviorScript.h:29` に記号付きで書いてあります）。

```
v     = L + h - Q                    // 親中心 → パーツ中心
v'    = Rot(θ) * (v.x*sx, v.y*sy)
world = P + (Q.x*sx, Q.y*sy) + v' - h*u
```

**`sx = sy = u = 1, θ = 0` を入れると `P + L` に還元されます。**
つまり**編集していない限り、既存のパーツ座標は1pxも変わらない**ことが数式で保証されます
（`BehaviorScript.h:61`）。回帰が無いことは、全パーツ座標の CSV ダンプ差分で実証しました。

**「後方互換を、テストではなく恒等式で保証する」**という話として使えます。

## 10. Scratch風ブロックエディタの実装（C#側）

命令カタログは **73種**（`Lab_Editor/Lab_Editor/BlockDef.cs:131`）。
C++ 側の op 数（数値30 / 真偽16 / 実行24 ＋ ハット3）と**完全に一致**します。

| ファイル | 責務 |
|---|---|
| `BlockDef.cs` | ブロックの種類カタログ |
| `BlockInstance.cs` | 置かれたブロック1個 |
| `BlockLayout.cs` | 2パスで寸法と座標を決める |
| `BlockRenderer.cs` | GDI+ で見た目を描くだけ |
| `BlockPaletteControl.cs` | パレット（検索・ツールチップ・ドラッグ元） |
| `BlockCanvasControl.cs` | 組み立てキャンバス（D&D・ソケット差込・ズーム） |
| `BlockScriptSerializer.cs` | ツリー ⇔ JSON AST |

- **レイアウトは2パス**（`BlockLayout.cs:4`）。Measure は子→親で寸法を、
  Arrange は親→子で座標を決めます。キャッシュも差分更新もせず毎回全部計算しますが、
  ブロック数が数百に達する想定ではないので十分です。
- **描画は GDI+。** 完全なジグソー型の輪郭は描かず、ヘッダ・背骨・フッタの重ね合わせで
  簡略表現しています。下側の凹は**キャンバスの背景色で塗るトリック**です。
- **D&D は OS の `DoDragDrop`。** 掴んだブロック以降をまとめて持ち上げる（Scratch と同じ）、
  ソケットは型で厳格に弾く（数値欄←ピル型、条件欄←六角形）、
  自分の中に自分を落とせないよう子孫を除外する、といった作りです。
- `BlockDef.cs:261` に運用上の警告が書いてあります。
  **カタログに未登録の op は、シリアライザが読み飛ばして保存時に無言で消えます。**
  エンジンに op を足したら必ずここにも足す、という決まりです。

## 12. 保存し忘れが起きない設計

タイマーによる自動保存は**ありません**。代わりに、
「一連の編集操作が終わった」というイベントごとに、**保存と Undo スナップショットを同時に**行います
（`Lab_Editor/Lab_Editor/Form1.cs:660`）。

Undo は**JSON往復のスナップショット方式**です。状態をそのまま持つのではなく、
一度 JSON 文字列にしてから積み、戻すときに復元し直します。
参照の使い回しによる意図しない書き換えが起きません。上限は50件。

## 13. 配布できるようにした話 ── 67箇所を書き換えなかった理由

アセットの参照は全てカレントディレクトリからの相対パスで、**約67箇所**あります。
動いていたのは Lab_Editor が作業ディレクトリを指定して起動していたからにすぎず、
**ゲーム単体では配布できない状態でした**。

「パス解決関数を作って67箇所を包む」案を採らなかった理由が2つ書いてあります
（`GamePaths.h:8`）。

1. 67箇所のうち10箇所は JSON 由来の変数パスで、**包み忘れてもコンパイルが通ります**。
   1箇所でも漏らすと「配布版でだけ特定の敵が見えない」という最悪の壊れ方をします。
2. 文字コード。リテラルは `/execution-charset:utf-8` で UTF-8 バイト列なので、
   exe のパス（CP932）とナロー文字列で連結すると混在して壊れます。

採った方法は、**exe の場所から最大8階層まで親を遡って `assets/enemies.json` を探し、
見つかった場所へカレントディレクトリを移す**というものです
（`GamePaths.h:37`、`GamePaths.h:53`）。書き換えは0箇所で、
開発フォルダでも配布フォルダでも同じバイナリが動きます。

セーブデータは `%LOCALAPPDATA%\LabProject01\` に置くので、
`Program Files` の下へ入れても権限エラーになりません。
